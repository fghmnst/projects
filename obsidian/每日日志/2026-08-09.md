### 主线（STM32）：工具链安装排障 + ST-Link 文档更新
- **apt 安装失败根因排查**：用户执行 `sudo apt install -y gcc-arm-none-eabi cmake stlink-tools openocd usbip` 时看到 4 行 "Checking for update using Github / Latest version is 1.13.4" 输出，误以为是 apt 报错
  - 真相 1：那 4 行是 **Obsidian AppImage 的更新检查日志**（electron-updater 打到 stdout，因从同一终端 `&` 启动混入），1.13.4 已最新，无关紧要
  - 真相 2：真正的 apt **整体失败了**——Ubuntu 没有独立 `usbip` 包（`apt-cache policy usbip` → Candidate: none，它属于 `linux-tools-*`），apt 遇到不存在的包直接 `E: Unable to locate package` 中止，其余 5 个包一个没装（`arm-none-eabi-gcc`/`cmake`/`st-flash`/`openocd` 全部 NOT FOUND）
- **修复方案交付**：去掉 usbip 重装 4 包 + 验证 3 命令（`arm-none-eabi-gcc --version` 期望 13.2.x / `st-flash --version` 1.8.0 / `openocd --version` 0.12.0）；usbip 改由 `linux-tools-generic hwdata` 提供，仅影响后续 USB 直通步骤，不影响编译
- **Obsidian 启动方式改进**：`APPIMAGE_EXTRACT_AND_RUN=1 ~/bin/Obsidian.AppImage >/dev/null 2>&1 &`，更新检查日志不再污染终端
- **ST-Link 文档全面更新**（用户确认已有 ST-Link V2，08-08 已知但 3 个文件仍写「待确认/待采购」）→ 3 个文件 6 处改动：

- **「重发推送给错日期」根因**（用户要求照新标准重发，Hermes 却给了 08-07 的旧推送）：①cron 与 QQ 对话是两个隔离世界，cron 原文从不进对话上下文；②"今天的"无事实依据，07:00 推送用户没 quote 过；③格式规范只在 memory 里（且 07:35 才写入，早于 07:00 执行），不在 cron prompt
- **三层修复**：
  1. **根治格式**：完整格式模板写入 cron prompt（`hermes cron edit d5ca32a14e37`，jobs.json 确认生效）——从此 07:00 自动推送自带规范，不依赖 memory
  2. **立即重发**：`hermes cron run daily-digest` → 10:23:50 `delivered to qqbot`，新格式投递成功
  3. **重发防错**：memory 方案 A——QQ 发指令让 Hermes 记住"推送原文在 `~/.hermes/cron/output/d5ca32a14e37/`，重发时先读目录"（是否写入成功未验证）
- **QQ markdown 渲染失败排查**（10:23 新格式推送渲染失败）：
  - 根因：QQ 官方 markdown 只支持**受限子集**——`#`/`##` 两级标题、`**加粗**`、`_斜体_`、`~~删除线~~`、`-`/`1.` 列表、`>` 引用、`***` 分割线；**不支持 `###`+ 三级标题、表格、代码块**
  - 时间线验证：旧格式（emoji+列表）渲染成功；10:23 新格式（`###`+表格）全挂
  - 修复：cron prompt 模板改 QQ 兼容写法（`##` 两级 + `**加粗**` 分类 + `-` 列表 + `***` 分隔线，显式禁 `###`/表格）→ 10:34:36 重发验证，输出无违规语法
