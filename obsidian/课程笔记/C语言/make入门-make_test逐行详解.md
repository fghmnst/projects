# make 入门：make_test 依赖关系与逐行详解（新手版）

> [!note] 一句话先行
> Makefile 是一张**图纸**：写清"每个产物由谁生成、先要谁最新、用哪条命令"。make 从默认目标倒推，逐个比时间戳，**只重做过期的那几步**。本笔记用 `make_test/`（`main.c` + `add.c` + `add.h` + `Makefile`）把这张图纸拆开揉碎，全部结论以实跑为准。

## 一、先建画面：图纸 + 只补坏零件

想象一辆车（可执行文件 `main`）的装配说明：

| 概念 | 比喻 | 本例 |
| --- | --- | --- |
| **目标（target）** | 要造出什么 | `main`、`main.o`、`add.o`、`clean` |
| **依赖（prerequisite）** | 先得有哪些零件 | `main.o` `add.o` / `main.c` `add.h` … |
| **命令（recipe）** | 怎么造 | `gcc …`、`rm …` |

开工时 make 先检查：目标在不在？零件有没有比目标更新？**缺的、旧的才动手**——这就是"增量构建"，也是 make 相对"每次全部重编"的价值。

## 二、依赖关系

分三层看：代码层（谁 include 谁）、构建层（Makefile 写的关系）、运行期（跑起来还靠谁）。

### 1. 代码层：`add.h` 是 main.c 和 add.c 的"合同"

```
main.c ──include──► <stdio.h>    系统头：printf 的声明
   │
   └──include──► add.h ◄──include── add.c
                   │                  │
        只放声明： int add(int,int);   │ 只放定义：{ return a+b; }
                                      ↓
                              编译产物 add.o（函数体的机器码在这里）
```

- **`main.c` 和 `add.c` 互相不认识**，谁也不 include 谁——它们只共同认识 `add.h`。
- `add.h` 是两者的**合同**：main.c 靠它知道"怎么调用 add"，add.c 靠它核对"我实现的签名对不对"。两边对不上，编译器当场报错。
- 各自的编译产物 `main.o`、`add.o` 最后由**链接器**对接。

### 2. 构建层：Makefile 描述的依赖图

```
main.c ─┐
        ├──► main.o ─┐
add.h  ─┤            ├──► main（可执行文件）
        ├──► add.o  ─┘
add.c ──┘
```

| 目标 | 依赖 | 命令做的事 |
| --- | --- | --- |
| `main` | `main.o` `add.o` | 链接成可执行文件 |
| `main.o` | `main.c` `add.h` | 编译 `main.c`（`-c`） |
| `add.o` | `add.c` `add.h` | 编译 `add.c`（`-c`） |
| `clean` | （无） | 删除产物 |

一个关键理解：**make 只比较时间戳，不看文件内容**。

- `.c` 出现在 gcc 命令行上，是真正的**编译输入**；
- `add.h` 出现在依赖里、却不在命令行上——它被 `#include` 抄进 `.c`，改了它编译结果就变，所以拿它的**修改时间**当"该重编了"的信号（头文件是预处理器自己找的，不需要写进命令）。

### 3. 运行期：还依赖共享库

实测 `ldd ./main`：

```
linux-vdso.so.1 (0x…)
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x…)
/lib64/ld-linux-x86-64.so.2 (0x…)
```

`add` 的代码在**链接时**已被拼进 `main`；`printf` 住在共享库 libc 里，由**动态链接器**在程序启动前接上。

### 4. 用 `nm` 看"谁提供了什么"（实测）

```
$ nm main.o add.o
main.o:  U add     ← U = undefined：引用了名字，还不知道实现在哪
         U printf
         T main    ← T = 本文件里定义了 main
add.o:   T add     ← 实现在这里
```

链接器的工作，就是把 `main.o` 的 `U add` 和 `add.o` 的 `T add` 对上号。

### 5. 增量构建实测（可复跑）

```bash
touch add.h && make
```

```
gcc -Wall -Wextra -std=c11 -c main.c -o main.o
gcc -Wall -Wextra -std=c11 -c add.c -o add.o
gcc -Wall -Wextra -std=c11 main.o add.o -o main
```

三条全跑：`add.h` 变新 → 两个 `.o` 过期重编 → `.o` 变新 → `main` 重新链接。

```bash
touch main.c && make   # 只重编 main.o，然后重新链接
make                   # make: 'main' is up to date.（无事可做）
```

## 三、这份 Makefile 是怎么想出来的（从手工流程倒推）

> [!tip] 别从语法正推
> Makefile 不是"编"出来的，是从你已经会做的手工流程**倒推**出来的。顺序：手工跑通 → 列出"输出 ← 输入 + 命令"表 → 机械翻译 → 补变量和头文件依赖。

### 1. 第 0 步：假设没有 make，你会怎么手工编译？

```bash
gcc -Wall -Wextra -std=c11 -c main.c -o main.o
gcc -Wall -Wextra -std=c11 -c add.c  -o add.o
gcc -Wall -Wextra -std=c11 main.o add.o -o main
./main
```

痛点：每改一个文件，都要**人脑判断**哪些命令该重跑——漏了就得到过期产物（老 `main.o` 配新 `add.o`，行为诡异）。于是有了需求：把"什么变了该重跑什么"写成机器能自动判断的声明。

### 2. 第 1 步：把手工命令抽象成三列表

每条命令都是同一个句式："**输出文件 ← 由谁生成 + 怎么生成**"。

| 输出（目标） | 输入（依赖） | 命令 |
| --- | --- | --- |
| `main.o` | `main.c` | `gcc … -c main.c -o main.o` |
| `add.o` | `add.c` | `gcc … -c add.c -o add.o` |
| `main` | `main.o` `add.o` | `gcc … main.o add.o -o main` |

### 3. 第 2 步：机械翻译

规则骨架就是三列表的翻译结果：

```
目标: 依赖1 依赖2
<TAB>命令
```

**先列手工命令表，再逐行翻译**——这就是"想到"这份 Makefile 的全部秘密。

### 4. 第 3 步：补三类"表格里没有、但正确性需要"的东西

| 补什么 | 动机 | 对应行 |
| --- | --- | --- |
| 变量 `CC` / `CFLAGS` | 同样的选项重复出现多次 → 抽成变量，改一处生效全部 | 1、2 |
| 头文件进依赖（`add.h`） | 问自己："改了哪些文件，这一步的**结果**会失效？"改 `add.h`，两个 `.o` 都过期。漏了它就是"改了头文件不重编"的阴间 bug | 7、10 |
| `clean` + `.PHONY` | 手工流程里还有"推倒重来"一步；它不产出文件，必须声明为伪目标 | 13–16 |

### 5. 开写前的"四连问"

写任何 Makefile 前先答这四个问题：

1. **最终要产出什么？** → 目标清单（可执行文件 `main`）
2. **每个产物的原材料是什么？** → 依赖（`.c`、`.h`、`.o`）
3. **每步手工命令是什么？** → 配方（照抄你手敲过的命令）
4. **哪些文件改了会让产物过期？** → 补全依赖，尤其头文件

### 6. 心智模型转换：声明式，不是脚本

| 错误直觉 | 正确直觉 |
| --- | --- |
| Makefile 是按行执行的脚本，我要安排顺序 | Makefile 是**依赖图声明**，执行顺序由 make 自己算 |
| 我要写"先编译、再链接" | 我只写"main 依赖两个 `.o`"；make 为了得到 main，自己递归去造 `.o` |

证据就在本文件里：`main` 的规则在 Makefile **最上面**（所以它是默认目标），编译规则在下面；但实跑时先执行的是 `gcc -c`。**你是倒着写、make 正着跑。**

### 7. 逐个"为什么这么写"（都是取舍）

| 写法 | 为什么 | 什么时候该变 |
| --- | --- | --- |
| 每个 `.c` 单独编成 `.o` 再链接 | 增量构建的前提：改哪个 `.c` 只重编哪个。一步 `gcc main.c add.c -o main` 也能跑，但没得省 | 文件多时必须分；文件极少时一步编译也合理 |
| 变量叫 `CC` / `CFLAGS` | make 的**内建惯例名**：内置隐式规则就引用这两个变量。冷知识：把第 8 行命令删掉，make 靠隐式规则照样能编 `.c → .o` | 保持惯例，不自创名字 |
| 依赖里放 `add.h` | make 只比时间戳、不看内容，头文件的影响必须**手写进依赖** | 工程变大后改用 `-MMD -MP` 自动生成依赖 |
| 链接命令也带 `$(CFLAGS)` | 图省事复用；严格说链接选项该用 `LDFLAGS`（`-Wall/-std` 对链接无意义但无害） | 想规范就拆成 `CFLAGS` / `LDFLAGS` |
| `rm -f` | 幂等：有产物没产物，`make clean` 都成功；构建脚本要能反复执行 | 不用改 |
| `.PHONY: clean` | 不产文件的目标必须声明，否则被同名文件骗过 | 所有不产文件的 target 都该标 |

### 8. 这份 Makefile 的"进化路线"

它停在"手写每条规则"阶段——**理解 make 的最佳阶段**。往后会自然长成：

1. **模式规则**：文件多到十个以上，`%.o: %.c` + 自动变量 `$@` `$<` 代替重复的编译规则；
2. **自动依赖**：`-MMD -MP` 让头文件关系自动写进 `.d` 文件，不再手写 `add.h`；
3. **目录与库**：`src/`、`build/` 分家，`LDFLAGS`、链接数学库等；
4. 再大就交给 **CMake 生成 Makefile**（STM32 已在用；参见 [[somezhishi/编程基础/构建工具链-CMake与make与Ninja详解|构建工具链笔记]]）。

## 四、Makefile 逐行（16 行）

规则骨架是：

```
目标: 依赖1 依赖2
<TAB>命令
```

含义：**要得到目标，先确保依赖都是最新的；依赖比目标新（或目标不存在），才跑命令。**

| 行 | 内容 | 逐行含义 |
| --- | --- | --- |
| 1 | `CC = gcc` | 定义变量 `CC`，后面用 `$(CC)` 引用。换编译器只改这一处；CC 是惯例名，make 有内置默认值。 |
| 2 | `CFLAGS = -Wall -Wextra -std=c11` | 编译选项变量：`-Wall` 打开常见警告、`-Wextra` 再开一批、`-std=c11` 用 C11 标准。这个名字不是 make 内置功能，靠下面手动 `$(CFLAGS)` 才会生效。 |
| 3 | （空行） | 只为人眼分组，make 忽略。 |
| 4 | `main: main.o add.o` | 第一条规则：目标是 `main`，依赖两个 `.o`。它同时是**默认目标**——敲 `make` 不带参数就从这里开始。 |
| 5 | `→ $(CC) $(CFLAGS) main.o add.o -o main` | 命令（行首必须是 **TAB**）。展开 = `gcc -Wall -Wextra -std=c11 main.o add.o -o main`。没有 `-c`，所以走**链接**步，`-o` 指定输出名。 |
| 6 | （空行） | |
| 7 | `main.o: main.c add.h` | "`main.o` 由 `main.c` 生成；且 `add.h` 一变新，`main.o` 就作废"。 |
| 8 | `→ $(CC) $(CFLAGS) -c main.c -o main.o` | `-c` = 只编译、不链接，产出**目标文件** `main.o`。 |
| 9 | （空行） | |
| 10 | `add.o: add.c add.h` | 同理。 |
| 11 | `→ $(CC) $(CFLAGS) -c add.c -o add.o` | 编译 `add.c`。 |
| 12 | （空行） | |
| 13 | `.PHONY: clean` | 声明 `clean` 是**伪目标**：它不产出文件，命令每次都要无条件执行。 |
| 14 | （空行） | |
| 15 | `clean:` | 没有依赖、也不产出文件的目标。 |
| 16 | `→ rm -f *.o main` | 删除所有 `.o` 和 `main`；`-f` = 文件本来就不存在也不报错。 |

两个新手必知的坑：

1. **命令行的 TAB**：第 5/8/11/16 行行首必须是真正的 TAB（本例是对的）。用空格会报 `*** missing separator`。
2. **`.PHONY` 防的坑**：如果目录里恰好有个叫 `clean` 的文件，make 会认为"目标已存在且不比依赖旧，无事可做"，删除命令就不执行了。

## 五、`add.h` 逐行（6 行）

| 行 | 代码 | 含义 |
| --- | --- | --- |
| 1 | `#ifndef ADD_H` | include guard 上半场：**如果**宏 `ADD_H` **没有**定义过，就继续读下面；定义过就一路跳到 `#endif`。 |
| 2 | `#define ADD_H` | 进来后立刻打标记：下次再被包含时，第 1 行判断为假，整个文件被跳过。 |
| 3 | （空行） | |
| 4 | `int add(int a, int b);` | **函数声明**（原型）：告诉编译器"有个函数叫 add，收两个 int，返回 int"。分号结尾、**没有函数体**。 |
| 5 | （空行） | |
| 6 | `#endif` | 与 `#ifndef` 配对收尾。 |

两个小提醒：

- 宏名已从 `FOO_H` 改为 `ADD_H`（2026-09-23）：哨兵名与文件名对应，读的人一眼知道它守卫谁。知识点不变——叫什么都行，**只要全局唯一**；惯例是"文件名大写 + `_H`"。
- 为什么需要 include guard：`add.h` 将来可能被多个头文件间接包含；重复的**声明**本身还好，但头文件里若有类型/变量的**定义**，重复就是编译错误。加哨兵一劳永逸（原理见 [[课程笔记/C语言/头文件include-尖括号与双引号的区别|头文件 include]] 第五节）。

## 六、`add.c` 逐行（6 行）

| 行 | 代码 | 含义 |
| --- | --- | --- |
| 1 | `#include "add.h"` | 把声明抄进来；同目录自己的头 → 双引号。**为什么 .c 也要包含自己的 .h？** 让编译器当场校对：声明与定义签名一致，不一致立刻报错。 |
| 2 | （空行） | |
| 3 | `int add(int a,int b)` | 函数**定义**的开头：返回 int、名字 add、形参 a 和 b（`a,int` 之间少个空格，风格问题，建议补）。 |
| 4 | `{` | 函数体开始。 |
| 5 | `return a + b;` | a、b 相加，`return` 把结果送回调用处。a、b 是**形参**——调用时收到的实参副本，改它们不影响调用者。 |
| 6 | `}` | 函数体结束。编译后，add 的机器码就躺在 `add.o` 里。 |

## 七、`main.c` 逐行（14 行）

| 行 | 代码 | 含义 |
| --- | --- | --- |
| 1 | `#include <stdio.h>` | 系统头，取 `printf` 的声明 → 尖括号。 |
| 2 | `#include "add.h"` | 自己项目的头 → 双引号。有了它，编译器才认识 add 的调用方式。 |
| 3 | （空行） | |
| 4 | `int main(void)` | 程序入口；返回 int 是**退出码**，`void` 表示不收命令行参数（对比 [[课程笔记/C语言/命令行参数-argc与argv入门|argc/argv 写法]]）。 |
| 5 | `{` | |
| 6 | `int a = 3;` | 局部变量 a，初值 3。 |
| 7 | `int b = 5;` | 局部变量 b，初值 5。 |
| 8 | （空行） | |
| 9 | `int result = add(a, b);` | **函数调用**三步：① 实参 3、5 拷贝给形参 a、b；② 跳到 add 的机器码执行（地址在链接时确定）；③ 返回值 8 赋给 result。编译期只需 `add.h` 的声明就能生成正确调用代码——这正是声明存在的意义。 |
| 10 | （空行） | |
| 11 | `printf("%d + %d = %d\n", a, b, result);` | 三个 `%d` 按顺序被 a、b、result 替换；`\n` 换行。**实测输出 `3 + 5 = 8`**。 |
| 12 | （空行） | |
| 13 | `return 0;` | 0 = 正常结束（实测 `echo $?` 得 **0**）。 |
| 14 | `}` | |

## 八、一句话把整条链串起来

`make` 按依赖图从 `main` 倒推：检查 `main.o`/`add.o` 是否比 `main.c`/`add.c`/`add.h` 旧 → 旧了就用 `gcc -c` 重编（此时 add.h 的声明被抄进两份 .c，stdio.h 的声明被抄进 main.c）→ `.o` 都比 `main` 新之后链接 → `./main` 运行时，`add` 直接调到已链接进来的代码，`printf` 由动态链接器连到 libc。

## 九、FAQ：删掉 `.o` 为什么还能跑？编译前后差在哪？

> [!question] 删掉 `main.o`、`add.o` 后，程序为什么还能运行？
> 答：`.o` 是**半成品零件**，`main` 是**组装好的整车**。链接器早已把 `.o` 里的机器码**复制合并**进 `main`；运行时操作系统只读 `main`，不会去找 `.o`。删 `.o` 只影响**下次构建**（make 会重新编译出来），不影响已生成的程序运行。

**三样东西的角色**（本机 `file` 实测）：

| 文件 | 是什么 | 内容 | 能单独运行吗 | 比喻 |
| --- | --- | --- | --- | --- |
| `main.c` | 源代码 | ASCII **文本** | 不能 | 图纸 |
| `main.o` / `add.o` | 目标文件（半成品） | 机器码 + 符号表，地址未最终定位（relocatable） | 不能 | 零件 |
| `main` | 可执行文件（成品） | ELF 可执行：有入口、地址已定、库已接好 | 能 | 整车 |

```
main.c: C source, ASCII text
main.o: ELF 64-bit LSB relocatable …        ← 半成品
main:   ELF 64-bit LSB pie executable …     ← 成品
```

**证据：链接 = 把定义"搬进"成品**（`nm` 实测）：

```
$ nm main.o | grep add
                 U add     ← U = undefined：只引用名字，实现在别处
$ nm main | grep add
000000000000119b T add     ← T = 已定义：add 的代码已经住进 main 里了
```

所以 `rm main.o add.o && ./main` 照样输出 `3 + 5 = 8`；而 `make` 一检查依赖，发现零件没了，就会重新编译。

**删除前 vs 删除后**：

| | 删除前 | 删除后 |
| --- | --- | --- |
| `.c` 源文件 | 不变 | **完全不变**（删 `.o` 不碰源码） |
| `main` 可执行文件 | 能跑 | 能跑（只要 `main` 还在） |
| `make` | `up to date` | 先重编缺失的 `.o`，再链接 |

反例：`make clean` 会连 `main` 一起删——**那时才真的不能跑**，要等 `make` 重建。

**编译前 vs 编译后**：gcc 内部走四步——

```
main.c --预处理--> 展开的源码 --编译--> .s 汇编 --汇编--> main.o --链接--> main
```

- `.c`：唯一事实源（你编辑的文本）；
- `.o`：机器码 + 符号表，但没入口、依赖没接全，**不能跑**；
- `main`：入口、地址、依赖都齐，**能跑**。

一句话：**菜谱 → 零件 → 整车**。零件留着是为了增量构建（改 `main.c` 只重造 `main.o`）；原料永远在、产物随时可再生，所以构建产物通常不提交 git。

**亲手验证**：

```bash
rm main.o add.o && ./main   # 照样输出 3 + 5 = 8
make                         # 重新编出两个 .o，再链接 main
```

## 术语小词典

| 词 | 大白话 |
| --- | --- |
| 目标（target） | 要生成的东西，冒号左边：`main`、`main.o`、`clean` |
| 依赖（prerequisite） | 先得最新的东西，冒号右边；make 只看它的时间戳 |
| 命令 / 配方（recipe） | 目标过期时执行的 shell 命令，行首必须是 TAB |
| 默认目标 | 文件里第一条规则的目标；`make` 不带参数时做它 |
| 伪目标（phony） | 不产出文件、每次无条件执行的目标（`.PHONY` 声明） |
| 增量构建 | 只重做"过期"的部分，靠比较时间戳实现 |
| 目标文件（`.o`） | 编译产出的半成品：机器码 + 符号表，还不能运行 |
| 符号表 / `nm` | `.o` 里的"谁定义了什么、谁引用了什么"清单 |
| 声明 vs 定义 | 声明 = 菜名（`;` 结尾）；定义 = 后厨做法（有 `{ }`） |
| 实参 vs 形参 | 实参 = 调用时给的 3、5；形参 = 函数里的 a、b（副本） |
| 链接（link） | 把多个 `.o` 和库拼成可执行文件，把 `U` 和 `T` 对上号 |
| 动态链接器 | 程序启动前跑的一小段，把 libc 等共享库接上（`ldd` 可看） |
| 退出码 | main 的返回值，告诉 shell 成不成功；`echo $?` 查看 |

## 自测

> [!question]- 想好再展开
> 1. 把 `add.h` 里签名改成 `int add(int a, int b, int c);` 后敲 `make`，会执行哪几条命令？为什么？
>    答：三条全跑。`add.h` 变新 → `main.o`、`add.o` 依赖过期先重编（此时两边签名不一致会当场报错）；两个 `.o` 变新 → `main` 重新链接。
> 2. 只 `touch main.c` 呢？
>    答：只重编 `main.o`，然后重新链接 `main`；`add.o` 不动。
> 3. `add.h` 为什么在 Makefile 里是依赖，却不在 gcc 命令行里？
>    答：命令行只编 `.c`；头文件是预处理器按 `#include` 自己找的。Makefile 列它纯粹为了用时间戳触发重编。
> 4. `clean` 前面为什么要 `.PHONY`？
>    答：防止目录里恰有个叫 `clean` 的文件时，make 误判"目标已最新"而不执行删除。
> 5. `main.c` 和 `add.c` 靠什么"认识"对方？
>    答：不互相认识；靠共同的 `add.h` 声明 + 链接器把 `add.o` 的定义接上（`nm` 里的 `U add` → `T add`）。
> 6. Makefile 里的命令为什么必须用 TAB 开头？
>    答：这是 make 的语法硬规定，用空格会报 `*** missing separator`；TAB 是 make 区分"规则行"和"命令行"的标志。
> 7. 用"四连问"设计：给程序加一对 `mul.c` / `mul.h`（实现 `int mul(int, int)`），Makefile 要动哪几处？
>    答：新增一条 `mul.o: mul.c mul.h` + 编译命令；`main` 的依赖加 `mul.o`；若 `main.c` include 了 `mul.h`，`main.o` 的依赖也加 `mul.h`。先列"输出 ← 输入 + 命令"表格再翻译，就不会漏。
> 8. 删掉 `main.o`、`add.o` 后，`./main` 和 `make` 各有什么反应？
>    答：`./main` 照常运行（成品里早已含 add 的代码，运行不查 `.o`）；`make` 发现依赖缺失，重新编译两个 `.o` 再重新链接。
