# 文件操作背后的系统概念：五个直觉（新手版）

> [!note] 一句话先行
> `opendir` / `readdir` / `stat` 背后没有魔法，只有五条常识：**程序是租客，内核是楼管兼前台**——办事要走窗口（系统调用）、办完发你号牌（文件描述符）、你的家当按楼层放（栈 / 堆 / 静态区）、CPU 有两个权限档位（用户态 / 内核态）、硬盘上的"名字"与"本体"分开登记（目录与 inode）。把它们串起来，你写 P1 的每一步都知道底层在发生什么。

## 〇、总画面：一栋楼 + 一个前台

想象你的程序住在一栋楼里，楼管（内核）在一楼开了一排办事窗口：

| 你代码里的东西 | 建筑比喻 | 底层机制 | 一句话 |
| --- | --- | --- | --- |
| `opendir` / `readdir` / `stat` | 敲前台的窗口 | **系统调用** | 程序没资格自己碰硬盘 |
| `DIR *` / `FILE *` | 取到的号牌 | **文件描述符（fd）** | 用完要还（`closedir` / `fclose`） |
| `char child[1024]` | 自己的格子间 | **栈** | 函数一返回就撕掉 |
| `malloc`（P2 才用） | 自由市场租地 | **堆** | 自己申请、自己归还 |
| `"用法：note-stats <目录>\n"` | 固定货架 | **只读数据区** | 程序一开张就摆好 |
| 路径 / 文件名 | 通讯录里的一行 | **目录 + inode** | 名字 ≠ 本体 |

下面五节，一节对应一条。

## 一、系统调用：找内核办事的窗口

**画面**：内核（kernel）是操作系统的心脏，是全机唯一有资格直接碰硬件的家伙。你想读目录，自己不能去动硬盘，只能走到它开的窗口前递单子："帮我把 `../../obsidian` 这个目录打开。"

- **谁在递单**：不是你的代码亲自去，而是 **libc**（C 标准库，`printf` 的老家）替你填好单子、敲窗。你写的 `opendir` / `readdir` / `stat` / `fopen` 都是 libc 的"代办服务"。
- **术语**：这次敲窗动作叫**系统调用（system call）**。
- **为什么必须这样**：安全。要是谁都能直接指挥硬盘，一个 bug 就能毁掉整个系统。
- **对应到你的代码**：`perror("opendir")` 能打出 `No such file or directory` 这种具体理由——那是内核拒办时写在单子上的（程序里叫 `errno`，错误编号）。
- **一个实用细节**：`readdir` 大多时候不用每次敲窗——libc 先用一次系统调用（`getdents64`）把一叠目录条目批发进**内部缓冲**，再一张张发给你。所以你拿到的 `entry` 指针指向的是那口公共锅：**下次 `readdir` 会覆盖它**。想留下名字要立刻 `snprintf` 拷走。

## 二、文件描述符：取号牌，用完要还

**画面**：窗口不会把整个目录/文件塞给你，它给你一张**号码牌**（一个小整数）；之后读、查、关，全凭号码办。内核替每个程序维护一张"在借牌号表"。

- **术语**：号码叫**文件描述符（file descriptor，fd）**。`opendir` 返回的 `DIR *`、`fopen` 返回的 `FILE *`，是 libc 在 fd 外面包的信封（信封上记着缓冲、读到哪了等备注），**内核只认里面的号**。
- **出生自带三张牌**（实测 `ls -l /proc/self/fd`）：

```
0 -> /dev/null        ← 标准输入 stdin
1 -> socket:[...]     ← 标准输出 stdout（这次运行被管道接走，所以是 socket）
2 -> socket:[...]     ← 标准错误 stderr
3 -> /proc/<pid>/fd   ← ls 读目录时临时借的第 4 张牌
```

在普通终端里跑，0/1/2 通常指向 `/dev/pts/N`（那块终端）；在管道/重定向里就指向管道或文件。**你写 `2>` 重定向之所以生效，就是"2 号牌被改指向了别处"**。`/proc/<pid>/fd` 是内核开的"围观窗口"，能看任意进程手上的牌。
- **为什么要还**：牌桌有上限（这台 WSL 实测 `ulimit -n` 是 1048576，看着用不完；服务器等环境常见 1024，且每张牌都占内核内存）。只借不还 = **句柄泄漏**，长期程序迟早借光、`opendir` 开始返回 NULL。所以大纲坑表里那条"递归不 `closedir` → 目录句柄泄漏"不是吓唬人。

## 三、进程内存布局：栈、堆、静态区

**画面**：程序一启动，内核给它分一栋楼，里面分区划片（实测 `cat /proc/self/maps`，节选）：

```
/usr/bin/cat    r-xp    ← 代码区：机器码（x = 可执行）
/usr/bin/cat    r--p    ← 只读数据区：字符串字面量住这
[heap]                  ← 堆
/usr/lib/.../libc.so.6  ← 共享库：printf 的实现运行时才接进来
[stack]                 ← 栈（maps 输出的最后一行）
```

- **栈**：一摞"自动贩卖机格子"。函数一调用就往下叠一层（放局部变量、参数、返回地址），函数一返回整层撕掉。**递归时"每层有自己的 `child[1024]`、自己的 `entry`"靠的就是这个机制**——不用 `malloc` 也有地方放家当。楼就这么大，叠几千层会"爆栈"。
- **堆**：自由市场，要多少自己申请（`malloc`）、用完自己还（`free`）。**P2 `prob-cli` 才来这里**。
- **静态区**：开张就摆好的固定货架——全局变量、字符串字面量（`"用法：..."` 这些就在只读区）。
- **和 STM32 的接口**：裸机没有操作系统帮你分楼，链接脚本 `.ld` 就是在**画这栋楼的图纸**（栈顶在哪、堆从哪开始）——不是凭空冒出来的概念。

## 四、用户态 / 内核态：CPU 的两个档位

**画面**：CPU 有一根权限拨杆。平时在**用户态（user mode）**：只能动自己楼里的内存，想碰硬件就是越权，当场崩。要办系统调用时，通过窗口切到**内核态（kernel mode）**，内核办完再把你拨回去。

- **为什么**：让"你的 bug"最多弄死你自己，而不是全系统。
- **衔接第一条**：所谓"敲窗"，物理上就是这次换挡。
- **怎么区分**：`strcmp`、`snprintf`、`strlen` 是纯内存计算，不用求谁；`opendir`、`stat`、`fopen`、`printf`（最终写出去）每次都在"过海关"。

## 五、名字 ≠ 本体：目录也是文件

**画面**：文件本体在硬盘上有个**门牌号**；"名字"只是登记在目录这本通讯录里的一行："名字 → 门牌号"。删掉一个名字只是撕掉一行，门牌还有引用就还在；同一个门牌也能挂多个名字（硬链接）。

- **术语**：门牌号叫 **inode**（索引节点）。实测证据：

```
$ stat obsidian/每日日志/2026-09-25.md
  Size: 2432       Inode: 1915     Links: 1
  Access: (0644/-rw-r--r--) ...
  Modify: 2026-09-25 ...

$ ls -i obsidian/每日日志/2026-09-25.md
  1915 obsidian/每日日志/2026-09-25.md
```

`stat` 命令和你的 `stat()` 函数查的是**同一份档案**：大小、门牌号、权限（chmod 改的就是这栏）、修改时间（步骤 5 的"近期改动"要用 `st_mtime`）。
- **目录本体是什么**：一种特殊文件，内容就是"名字 → 门牌号"那张表。`readdir` = 念通讯录（所以只给名字）；`stat` = 拿名字查档案（所以能知道是不是目录、多大、何时改）。
- **`.` 和 `..` 为什么必然存在**：每本通讯录都有两行固定条目——"." 指自己、".." 指上级。这就是遍历时不跳过它会无限套娃的原因：`..` 领你回上一级，再念到你这个子目录，又进来……循环。
- **路径为什么能一段段拼**：路径是一串名字；内核从根（或当前目录）出发，翻一层通讯录找到一个名字，再翻下一本。

## 六、把一条命令拍成电影

`./note-stats ../../obsidian` 回车后，底层依次发生：

1. `opendir`：libc 替你递单 → CPU 切内核态 → 内核翻通讯录打开目录 → 返回一个 fd，包成 `DIR *`；
2. `readdir`：从 libc 的内部缓冲念一个名字（缓冲空了就再敲一次窗批发一叠）；
3. `snprintf` 拼出完整路径 → `stat` 按路径查档案（是不是目录、多大、何时改）；
4. 是目录 → **递归**：栈上叠一层新格子、再借一张 fd 牌；
5. 是 `.md` → `printf` 输出路径；
6. 每层走完 `closedir` 还牌 → `return` 撕格子；
7. main 返回退出码，shell 用 `echo $?` 看它。

## 七、40 秒亲手实验

```bash
ls -l /proc/self/fd              # 看牌桌：0/1/2 指向哪？
cat /proc/self/maps | tail -5    # 楼的最底下一行：[stack]
ls -i obsidian/每日日志/*.md     # 看门牌号（第一列数字）
stat obsidian/每日日志/*.md      # 看档案：权限 / 大小 / 修改时间
```

## 术语小词典

| 词 | 大白话 |
| --- | --- |
| 内核（kernel） | 操作系统的心脏，全机唯一能直接碰硬件的部分 |
| 系统调用（syscall） | 程序请内核办事的"窗口递单"动作；`opendir` 等最终都走到它 |
| libc | C 标准库；把系统调用包装成好用的函数（`printf`、`opendir` 都是它提供的） |
| `errno` / `perror` | 内核拒办时留下的错误编号 / 把它翻译成人话打印出来 |
| 文件描述符（fd） | 内核发的"号牌"（小整数）；`DIR *` / `FILE *` 是包着 fd 的信封 |
| 句柄泄漏 | 借了牌不还，牌桌被占光，后续 `opendir` / `fopen` 失败 |
| 用户态 / 内核态 | CPU 的两个权限档位；碰硬件必须切到内核态 |
| 栈 / 堆 | 自动叠放的格子间（局部变量、递归每层） / 自己申请归还的自留地（`malloc`） |
| 静态区 / 只读数据区 | 程序一开张就摆好的固定货架；字符串字面量住这 |
| inode | 文件在硬盘上的"门牌号"；名字只是通讯录里指向它的条目 |
| 硬链接 | 同一个 inode 挂多个名字；`stat` 里的 `Links` 计数 |
| `getdents64` | 内核"批发一叠目录条目"的系统调用，`readdir` 的底层 |
| `/proc` | 内核开的一扇窗，能围观进程的牌桌（`fd`）、楼层（`maps`）等 |

## 自测

> [!question]- 先自己答，再展开
> 1. 漏写 `closedir` 的后果，用"牌"的语言描述？
>    答：借了号牌不还；牌桌数量有限（且每张占内核内存），借光之后 `opendir` 开始返回 NULL——这就是句柄泄漏。
> 2. 递归时每层的 `child[1024]` 互不覆盖，靠的是哪个机制？
>    答：栈。每次函数调用叠一层新格子，局部数组住在自己那层里；函数返回整层撕掉。
> 3. `readdir` 和 `stat` 的分工，用"通讯录 / 档案"的语言说一遍？
>    答：`readdir` 念通讯录——只给你名字（`d_name`，不带路径）；`stat` 拿名字查档案——告诉你本体是目录还是文件、多大、何时改。
> 4. 为什么 `perror` 能打印出具体错误原因，而 `strcmp` 出错时没有这种东西？
>    答：`perror` 的事是内核办的（系统调用），内核拒办时会写下 `errno`；`strcmp` 是纯内存计算，压根没求过内核。
> 5. 遍历目录时为什么必须先跳过 `.` 和 `..`？
>    答：它们是每本"通讯录"里固定指向自己和上级的条目；`..` 会把递归带回上一级，来回循环、无限套娃。
